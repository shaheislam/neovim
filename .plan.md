## Approach

2. Define tool ownership for learning, investigation, delivery, and review
3. Make `.plan.md` and the Neovim bridge explicit parts of the steering model
4. Link the workflow contract from the docs that agents and contributors already read
5. Verify the updated guidance is consistent and easy to find

## Key Decisions

- This repo should document a workflow contract instead of adding another orchestration layer.
- `.plan.md` should be treated as the control plane for steering active AI work.
- The Neovim bridge and diagnostics should be described as shared state inputs to external harnesses, not as a standalone orchestration system.
- Learning, investigation, delivery, and review should each have a primary tool owner.

## Success Criteria

- The repo has a single documented workflow contract at `.claude/context/workflows.md`
- `CLAUDE.md` and `AGENTS.md` both point to that contract
- The control plane, delivery plane, and review plane are explicitly defined
- Agents are no longer told to run the invalid `bd sync` command

## Current State

The repo already had the technical primitives needed for a cohesive AI workflow: Neovim bridge state, hotreload, `.plan.md`, multiple AI front-ends, and a review surface via diagnostics and diff tooling. What it lacked was an explicit contract explaining how they fit together.

That contract now lives in `.claude/context/workflows.md` and is linked from `CLAUDE.md` and `AGENTS.md` so both humans and agents see the same routing and steering rules.

## Failed Approaches
